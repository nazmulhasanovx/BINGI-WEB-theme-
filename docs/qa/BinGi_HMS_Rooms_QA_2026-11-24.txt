HOW TO READ
  P0 = blocker, wrong room state, or money / double-booking risk.
  P1 = wrong, risky, or different from approved design.
  P2 = polish.
  Each item: WHERE / HAPPENS / IMPACT / EXPECTED / FIX (BE = backend,
  FE = frontend).

TOTAL: 5 x P0 | 10 x P1 | 9 x P2 | + design gaps per screen (section E)

ROOT CAUSE IN ONE LINE
  Room state lives in TWO places that disagree:
   (1) legacy rooms table  (/api/rooms  -> status RESERVED/OCCUPIED/
       DIRTY/HOLD per room number), and
   (2) new accommodations engine (/api/accommodations/* -> units,
       categories, "tonight" state).
  Screens read from different places, so the same room shows
  different truth on different screens. Most items below come from
  this. Fix the source of truth first, then the screens.

[P0-01] Rooms shown "Booked tonight / Guest in room" with NO guest
  WHERE    Room numbers: 101, 102 (also 208, 209). Room types card
           "Fully booked tonight" for the 101-105 type.
  HAPPENS  101 and 102 have no checked-in booking for tonight.
           Opening 101 -> Reservation schedule says: "Unit is marked
           occupied, but no matching current checked-in canonical
           owner was found ... Handoff review is incomplete."
           102 is held by WBK-2026-000043 (stay 2-3 Nov, never
           checked out). 208 by WBK-000064 (4-5 Nov), 209 by
           WBK-000010 (9-10 Sep). 101: legacy status OCCUPIED, no
           booking at all.
  IMPACT   4 sellable rooms are blocked from sale every night. The
           count "Booked tonight 6" is really 2 (103, 104).
  EXPECTED Booked tonight = rooms with a booking that covers tonight.
  FIX      BE: derive "booked/occupied" only from bookings, never
           from a stored room status. One-time cleanup of legacy
           OCCUPIED flags. FE: if a room has an "orphan" state,
           show "Needs review" with a one-click "Release room".

[P0-02] Overdue in-house guests are invisible (no "Overdue check-out")
  WHERE    Room numbers, Room types, Housekeeping, API
           /api/accommodations/tonight (overdue_checkout = 0 for all).
  HAPPENS  5 bookings are still CHECKED_IN after their check-out date:
             WBK-000077 room 104  out 20 Nov
             WBK-000064 room 208  out 5 Nov
             WBK-000043 room 102  out 3 Nov
             WBK-000011 room 206  out 12 Sep
             WBK-000010 room 209  out 10 Sep
           No screen flags any of them.
  IMPACT   Front desk never sees who must leave or be extended; room
           charges for extra nights are never posted (money leak);
           rooms stay blocked or are double-sold (P0-03).
  EXPECTED Prototype: "Due out" / "Overdue" chip on the room and a
           red count on the KPI row; Dashboard "Departures" includes
           overdue.
  FIX      BE: compute overdue_checkout = status CHECKED_IN and
           check_out < business date. FE: red "Overdue check-out"
           chip + filter; Night audit should list them.

[P0-03] Room 206 shown "Available" while a guest is checked in
  WHERE    Room numbers 206 = "Available / Room clean". Room types
           card "2 of 4 available" counts it.
  HAPPENS  WBK-2026-000011 is CHECKED_IN on 206 (never checked out).
           Legacy /api/rooms says 206 AVAILABLE, so the screen sells
           it. In the Bookings test, "Move room" also offered 206.
           Room 104 has TWO checked-in bookings at the same time
           (WBK-000077 and WBK-000079).
  IMPACT   Double booking / two guests given the same room.
  EXPECTED A room with a CHECKED_IN booking is never "Available".
  FIX      BE: availability must check CHECKED_IN bookings (and
           block check-in to a room that already has a checked-in
           guest). Same rule for Move room and New booking.

[P0-04] Editing ANY room type fails (422) - price ৳16 cannot be fixed
  WHERE    Room types -> Edit (opens "Edit Room" drawer) -> Update Room.
  HAPPENS  Tested on Deluxe (৳16 -> ৳16,000) and on Premium Room with
           NO change. Both: POST /api/rooms/RM-HTL000001-xxx -> 422
           "The selected bed is invalid. (and 5-6 more errors)".
           Rejected values: bed "Twin Bed"; amenities free_wifi,
           free_parking, fitness_center, swimming_pool, 24_7_security,
           room_service. The form offers exactly these values.
           The error is shown with a browser alert() popup.
  IMPACT   Hotel cannot change price, photos, amenities or meals of
           any existing room type. Deluxe stays on sale at ৳16/night.
  EXPECTED Save works; validation lists match the form options.
  FIX      BE: align validation enums with the bed/amenity master
           list (or accept stored legacy values). FE: replace
           alert() with inline field errors (alert also freezes the
           browser tab - we lost the tab once while testing).

[P0-05] Out-of-order state comes from two places that disagree
  WHERE    Room numbers / Room types vs Housekeeping > Maintenance.
  HAPPENS  a) Room 202 = "Not for sale / Maintenance" (legacy HOLD),
              but its panel says "This room has no open maintenance
              report. Review it in Housekeeping." Housekeeping shows
              Room blocks 0 and no ticket for 202. There is no button
              anywhere to release 202.
           b) Room 207 has an OPEN, URGENT maintenance ticket
              (mnt_dsz2mpsrwn "ggg", target 9 Nov, overdue) with room
              block Off -> 207 shows "Available / Room clean" and has
              a confirmed booking (WBK-000080, 26-28 Nov).
           c) Room types card for 312 shows badge "Out of order"; 312
              is only dirty.
  IMPACT   One room is lost from sale forever; another is sold with an
           urgent open fault; staff see three different answers.
  EXPECTED One source: an OOO block always has a maintenance record,
           shows on the room with reason + expected back date, and
           has "Release". An urgent open ticket shows a warning on
           the room even when not blocked.
  FIX      BE: migrate legacy HOLD to a maintenance block record (or
           clear it). FE: 202 panel gets "Release room"; card badge
           must use the same OOO field as the room list.
